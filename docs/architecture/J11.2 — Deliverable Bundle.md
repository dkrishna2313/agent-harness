# J11.2 — Deliverable Bundle

**Status:** Complete. Additive milestone — no prompts, reasoning, Functional
Agent Contracts, boundaries, CLI surface, or existing deliverable behaviour

**Date:** 2026-07-03

---

## 1. Motivation

J11.1 validated the Deliverables Framework seam by registering a second
generator (`ExecutiveBriefGenerator`) alongside the first
(`MarkdownReportGenerator`). Both share the same `default_registry` and the
same completed `AgentContext` — but producing them required two independent
`registry.generate()` calls with no shared envelope for the pair.

J11.2 introduces that envelope: `DeliverableBundle`, the canonical business
object representing the complete output of one engagement's presentation
phase, and `DeliverableBundleGenerator`, the orchestrator that drives N
generators over one context and assembles the result.

## 2. What shipped

### New file — `functional_agents/deliverables/bundle.py`

#### `DeliverableBundle`

```python
@dataclass
class DeliverableBundle:
    bundle_id: str = ""
    engagement_id: str = ""
    reasoning_graph_id: str = ""
    created_at: str = ""
    deliverables: list[DeliverableArtifact] = field(default_factory=list)
    metadata: dict[str, Any] = field(default_factory=dict)

    def to_dict(self) -> dict[str, Any]: ...
```

`to_dict()` always emits `"generated"` (the serialised artifact list),
omits empty optional fields (`engagement_id`, `reasoning_graph_id`,
`created_at`, `metadata`), and round-trips through JSON.

#### `DeliverableBundleGenerator`

```python
class DeliverableBundleGenerator:
    def __init__(self, registry: DeliverableRegistry | None = None) -> None: ...

    def generate(
        self,
        context: AgentContext,
        deliverable_types: list[str],
        output_dir: Path,
        *,
        bundle_id: str = "",
        engagement_id: str = "",
        created_at: str = "",
    ) -> DeliverableBundle: ...
```

Responsibilities:
- Invokes each requested generator independently via the registry
- Assigns a bundle-scoped artifact `id` (`bundle_id[:8]-{type}`)
- Assembles and returns a `DeliverableBundle`
- Sets `context.deliverable_bundle = bundle.to_dict()` (presentation state only)

File naming convention: `executive_brief` → `executive-brief.md`
(underscores replaced by hyphens).

No Functional Agents are invoked. No LLM call is made. No reasoning field on
`AgentContext` is mutated.

### `functional_agents/deliverables/__init__.py`

Added `DeliverableBundle` and `DeliverableBundleGenerator` to public exports.
`default_registry` unchanged.

### `functional_agents/context.py`

One additive field after `deliverables`:

```python
deliverable_bundle: dict[str, Any] = field(default_factory=dict)
```

Set by `DeliverableBundleGenerator` when a bundle is generated; empty
(`{}`) otherwise — identical JSON-serialisability convention as every
other `AgentContext` field.

### `functional_agents/pipeline_trace.py`

One additive top-level key in `build_canonical_trace()`:

```python

```

`None` when no bundle was generated; the bundle dict (same shape as
`bundle.to_dict()`) when it was. Not added to `_REQUIRED_TOP_LEVEL_KEYS`
— pre-J11.2 canonical traces remain valid.

### CLI — unchanged

`functional_agents.cli run --engagement ...` is unchanged. `ReportAgent`
still defaults to producing only the `"markdown"` deliverable. The bundle
generator is a new capability available via direct API.

## 3. Design decisions

- **`DeliverableBundleGenerator` is not a `DeliverableGenerator` subclass.**
  `DeliverableGenerator` represents one generator per deliverable type (the
  leaf). The bundle orchestrator is a higher-level object with a different
  contract (`generate(context, types, output_dir)` vs
  `generate(context, output_path)`) — inheritance would misrepresent the
  relationship and pollute `DeliverableRegistry`.
- **Registry is resolved lazily in `_resolved_registry()`.** `bundle.py`
  imports from `registry.py` but not from `__init__.py` (which imports
  `bundle.py`), breaking the circular import at module load time.
- **Artifact id assigned by the bundle generator, not the individual
  generators.** Individual generators don't know their bundle context.
  The bundle generator stamps each artifact `id = bundle_id[:8]-{type}`,
  giving each a globally-scoped, stable identifier.
- **`context.deliverable_bundle` is presentation state, not reasoning
  state.** Setting it in `generate()` is the same category of mutation as
  `ReportAgent` appending to `context.deliverables` — it records that
  presentation work happened without touching any reasoning field
  (`risks`, `assumptions`, `recommendations`, etc.).
- **`deliverables` trace key unchanged.** The existing `deliverables` list
  in the canonical trace (populated by `ReportAgent`) is preserved. The
  bundle adds a parallel `deliverable_bundle` key rather than replacing
  the list — additive, backward-compatible.
- **`output_dir.mkdir(parents=True, exist_ok=True)` inside `generate()`.**
  Callers should not need to create the directory beforehand; the bundle
  generator handles it.
