# J11.0 — Strategic Deliverables Framework

**Status:** Complete. Additive architectural milestone — no prompts,
reasoning, Functional Agent Contracts, Research Object, Decision Model,
report content/section logic, boundary schemas, performance instrumentation,
or CLI surface changed. Existing markdown report output is byte-for-byte
identical (verified below). 2499 tests pass (19 new).

**Date:** 2026-07-03

---

## 1. Motivation

The platform has completed the Knowledge Platform, Functional Agent
Platform, Strategic Reasoning Platform, Engineering Platform, and Developer
Tooling. The next phase is to separate **reasoning** from **presentation**
so multiple consulting deliverables (executive briefs, board papers,
investment memos, strategy decks, ...) can be generated from the same
Strategic Reasoning Graph — the accumulated assumptions, risks,
opportunities, hypotheses, recommendations, strategic options, and decision
analysis that already live on `AgentContext` — without rerunning research.

Before J11.0, `ReportAgent` both *decided what markdown to write* and *wrote
it* in one inline block. There was no seam a second deliverable (a deck, a
memo) could hook into without duplicating that reasoning-to-text logic.
J11.0 introduces that seam and makes the existing markdown report its first
concrete implementation.

## 2. What shipped

### New package — `functional_agents/deliverables/`

```
functional_agents/
    deliverables/
        __init__.py
        base.py
        registry.py
        request.py
        artifact.py
        markdown_report.py
```

- **`request.py`** — `DeliverableRequest(id="", type="markdown", audience="",
  title="", format="markdown", options={})`. Intentionally minimal — only
  `type` drives dispatch today; `audience`/`title`/`format` are inert for
  `MarkdownReportGenerator` but exist so future generators can read caller
  intent without another contract change. `to_dict()`/`from_dict()`
  round-trip it as a plain dict, matching every other `AgentContext` field's
  JSON-serializable convention.
- **`artifact.py`** — `DeliverableArtifact(type, id="", path=None,
  mime_type="", metadata={})`. The canonical output object for every future
  deliverable. `status` is not a dataclass field (the canonical field list
  is `id`/`type`/`path`/`mime_type`/`metadata`) — generators report it via
  `metadata["status"]`; `to_dict()` projects it back out as a top-level
  `"status"` key (default `"generated"`), matching the trace's
  `{"type": ..., "status": ...}` shape without duplicating it inside the
  emitted `metadata`.
- **`base.py`** — `DeliverableGenerator(ABC)`, one method:
  `generate(context: AgentContext, output_path: Path) -> DeliverableArtifact`.
  A generator may only *read* the Strategic Reasoning Graph on `AgentContext`
  and write to `output_path`; it must never run new reasoning, call an LLM,
  mutate reasoning fields, or invoke a Functional Agent.
- **`registry.py`** — `DeliverableRegistry`: `register()`, `get()` (raises
  `KeyError` naming the registered types on a miss), `generate(context,
  request, output_path)` — dispatches on `request.type` to
  `generator.generate(context, output_path)`.
- **`markdown_report.py`** — `MarkdownReportGenerator`, `deliverable_type =
  "markdown"`. Calls `report_agent.build_markdown_report_content(context,
  memo)` for the text, then `research_agent.markdown.write_markdown()` for
  the disk write — the same two calls `ReportAgent` always made, now behind
  the generator seam. Sets `mime_type="text/markdown"` on the artifact.
- **`__init__.py`** — exports the public names and `default_registry`, a
  `DeliverableRegistry` pre-registered with `MarkdownReportGenerator` under
  `"markdown"`.

### `functional_agents/context.py`

Two additive fields, following the existing dict/list convention every
other `AgentContext` field uses:

```python
deliverable_request: dict[str, Any] = field(default_factory=dict)
deliverables: list[dict[str, Any]] = field(default_factory=list)
```

### `functional_agents/report_agent.py`

- **Extracted** `build_markdown_report_content(context, memo) -> str` — a
  pure, module-level function containing the exact J7.6b executive-report /
  legacy memo-based branching that used to run inline in `ReportAgent._execute`.
  No logic changed; a cut-and-paste extraction (verified byte-identical
  below).
- **`ReportAgent._execute`** no longer builds/writes markdown directly:
  1. Stashes the boundary-typed `memo` on `context.trace["_report_memo"]`
     (scratch, like every other `_`-prefixed trace key).
  2. Builds a `DeliverableRequest` from `context.deliverable_request` (or a
     default `"markdown"` request).
  3. Calls `default_registry.generate(context, request, self._out_path)`.
  4. Appends the resulting artifact to `context.deliverables`.
  5. Reads `report_path`/`trace_path` off the artifact — identical to the
     pre-J11.0 `context.artifacts` assignment.

### `functional_agents/pipeline_trace.py`

`build_canonical_trace()` gains one additive top-level key:

```json
"deliverables": [{"type": "markdown", "status": "generated"}]
```

sourced verbatim from `context.deliverables`. Not added to
`_REQUIRED_TOP_LEVEL_KEYS` — a pre-J11.0 canonical trace remains valid.

### CLI — unchanged

No CLI changes in this milestone. `functional_agents.cli run` (including
`--engagement`) remains the end-to-end entrypoint; `functional_agents.run_agent`
remains the isolated engineering-validation harness. The CLI architecture is
considered stable.

## 3. Design decisions

- **Package split matches the spec exactly.** `DeliverableRequest` and
  `DeliverableArtifact` live in their own `request.py`/`artifact.py` modules
  rather than sharing `base.py`, so `base.py` holds only the generator
  contract.
- **`DeliverableGenerator.generate(context, output_path)`, not
  `generate(context, request)`.** This milestone's spec fixed the exact
  signature via its own example, and — unlike an earlier draft of this
  milestone that used `(reasoning_graph, output_directory)` — `output_path`
  is a full destination file path, not a directory. That resolves the
  earlier tension cleanly: `ReportAgent` passes its already-resolved
  `self._out_path` straight through, so the default markdown deliverable's
  filename is guaranteed unchanged with no compromise needed.
  `DeliverableRequest` still exists and is still recorded on
  `AgentContext.deliverable_request` (for audit/trace and future generator
  intent), but the concrete `generate()` call for this milestone does not
  thread it into the generator — the registry uses `request.type` purely for
  dispatch.
- **`status` lives in `metadata`, not as a bare field.** The canonical field
  list for `DeliverableArtifact` is `id`/`type`/`path`/`mime_type`/`metadata`
  (no `status`). `to_dict()` derives `"status"` from
  `metadata.get("status", "generated")` so the trace shape
  (`{"type": ..., "status": ...}`) still comes out right without adding a
  field the spec didn't list.
- **Extraction, not reimplementation.** `build_markdown_report_content()` is
  a literal cut of the pre-J11.0 branching out of `_execute` into a
  module-level function. This is what makes "byte-for-byte identical" a
  mechanical guarantee rather than a hope.
- **`memo` travels via `context.trace`, not a new context field.** Same
  `_report_memo` scratch-trace convention as `_memo`/`_perf_tracker` —
  avoids adding a non-serializable `ResearchMemo` object to a real
  `AgentContext` field.
- **Generators never invoke Functional Agents.** `MarkdownReportGenerator`
  imports `report_agent.build_markdown_report_content` — a pure function —
  but never the `ReportAgent` class, and never `FunctionalAgent`. Verified
  by an AST-based test (`test_markdown_report_generator_never_touches_functional_agents`),
  not just by inspection.
- **No LLM boundary for `MarkdownReportGenerator`.** It calls no LLM — it
  renders already-validated reasoning state — so a boundary would add
  ceremony with no failure mode it protects against. Future generators that
  *do* call an LLM should adopt PH2's Universal LLM Boundary pattern then.
- **No CLI changes.** Per the spec, the CLI architecture is now stable;
  `functional_agents.cli run --engagement ...` is the validated end-to-end
  path and needed no modification to exercise this milestone.
